# Results (Chapter 3): what persists after access is revoked, and does anything signal it

Seven phases (P1–P7), 36 conditions (phase × config × variant), run against
two local **Community Solid Server 7.2.0** instances: one with **WAC**
(`:3100`) and one with **ACP** (`:3101`). In every phase, alice grants a
recipient app (appR) read access to `person.ttl`, then revokes it. We
measure what still reaches appR, or anyone else, afterwards: through CSS
directly, a caching proxy, notification channels, a query engine, a copying
aggregator, an agent's retrieval memory, and a withdrawal notice. Every
prediction was committed to `ch3/HYPOTHESES.md` before the first counted run
of its phase.

**What the numbers cover.** Every condition ran **twice**, as full run 1
(2026-09-24 for P1–P5, 2026-09-28 for P6 and P7 v1, 2026-09-29 for P7 v2) and
full run 2 (from a fresh `npm run exp:setup -- --reset`, 2026-09-28; P7 v2 on
2026-09-29). Each condition has **10 counted runs per full run**: **720
counted raw files**, 0 failed. `npm run exp:check` and `npm run exp:compare`
exit 0. Each condition produced **one** distinct categorical outcome, the same
in both full runs.

**22 raw files are kept but not counted**, each listed with its reason in
`raw/EXCLUDED.tsv`, and each is described in `OBSERVATIONS.md`:

- 7 P2 runs (wac/proxyA, 2026-09-24): an instrument fault. With no upstream
  keepalive, Docker Desktop's container-to-host network stalled. We fixed the
  nginx configs and reran P2.
- 15 full-run-2 runs that spanned a macOS system suspend, so their timed
  windows are invalid: p3/acp ×4, p4/wac/b ×1, p5 ×5, p6/wac/rag ×5. Each was
  replaced by a make-up rep (r11 and up).

`CLAUDE.md`, and the three stay distinct. *Enforced*: CSS changed its
behaviour (a `403`). *Advertised*: CSS stated a permission it does apply (the
`WAC-Allow` header). *Declared only*: metadata that no decision uses (the P7
notice, including its DPV consent status). "**not enforced**" marks a path
along which the data kept flowing after the revoke. None of those paths was a
read from CSS itself.

## In plain language

**At the server, revocation works, and at once.** With both access-control
systems CSS 7.2.0 ships (WAC and ACP), the first request appR sent after
alice's revoke was refused (P1, 20/20 runs per config across both full runs).
appR's access token was still valid, and it did not matter. A query engine
that had already read the data asked the server again, and was refused (P4).
Nothing stale ever came from CSS itself.

**Everything that already left the server stays out of reach.** Access
control governs requests to a URL. It does not reach data that a request
already carried away. A simple aggregator kept all 23 copied rows after the
revoke (P5 naive). A retrieval memory built while access was valid kept all 10
of its chunks from the resource. After the revoke it still ranked a chunk of
the revoked resource first for all 10 questions, and a small local language
model (`qwen2.5:3b`) answered all 10 correctly from them (P6). A
deliberately permissive caching proxy (config B, written for this experiment)
kept serving the revoked resource for about 60 seconds. It served appR, and
it also served an anonymous client that CSS itself refused (P2). The server
sent nothing to any of them.

**Notification channels keep running after the permission is gone.** appR
could no longer read `person.ttl`, and a new subscription to it was refused.
But the WebSocket and Webhook channels opened before the revoke delivered all
20 of alice's later changes (P3). Reconnecting to the old channel address
needed no credentials. alice could not find these channels herself. Anyone
who knew a channel's id could end it: bob, an anonymous client, or alice once
she was given the id (P3 unsub).

**Nobody is told that access ended.** No component received any message
about the permission change (P3). The refusal appR receives is identical,
status, body and headers, whether access was withdrawn, never granted, or the
resource was deleted (P5). The query engine's error does not mention access
at all (P4). A recipient learns of a revoke only if it asks again and is
refused.

**A withdrawal notice works only when the recipient chooses to act on it.**
In P7 alice sent both recipients a notice to their inboxes. It arrived in
about a second, a delay set by our handler's 1 s polling. A cooperating
recipient deleted everything, and a non-cooperating one kept everything. Both
were written for this experiment. alice's view was identical in both cases:
`201` for the notice, then `403` when she tried to look at it. She had to
take the recipient list from her own grant log, because after the revoke
nothing on the server named the former recipients. Adding a machine-readable
DPV "consent withdrawn" status to the notice (v2) changed nothing that any
party did. It is **declared only**. It reached the recipients intact, in
160/160 receptions, and no component used it.

The pattern across P1–P7: CSS 7.2.0 **enforces** the revoke on every request
made to it. Every copy, index, cache and channel that existed before the
revoke lies outside that enforcement. Whether those copies are removed depends
only on recipient-side code that the pod cannot see, and cannot verify.

## Predictions and corrections

- **Wrong: H4.2.** We predicted that a reused Comunica engine would answer
  from its cache without asking for `person.ttl` again. It asked again and got
  `403` (P4). The reason was not traced in the Comunica source.
- **Partly wrong: H3.7.** After a channel expired, reconnecting to it was
  *accepted* at the WebSocket handshake, not refused. The socket then stayed
  silent (P3 `short`).
- **Imprecise wording: H7.12.** It said "byte-for-byte". What was compared is
  alice's statuses and response header names, which matched.
- **Instrument corrections, not findings:** the 7 excluded P2 runs (Docker
  Desktop network stall), and the 15 runs excluded for spanning a system
  suspend. The suspend criterion was added after those runs happened (commit
  `51983dd`). One of the 15, `p4/wac/b` r05, failed with CSS HTTP 500
  `Lock expired after 6000ms` right after a 143.1 s suspend. We infer, but have
  not shown, that the suspend caused it. Instrument additions made before the
  counted runs are listed per phase in `OBSERVATIONS.md`.

All other predictions (H1–H7) matched.

## Limitations

- **One server implementation, two configurations.** Every claim is scoped to
  CSS 7.2.0 with the WAC or ACP config in `ch3/config/`. Other servers, and
  Inrupt ESS with Access Grants (P8, not run), may behave differently.
- **One machine, localhost, one fixture.** The timings (≈1 s notice latency,
  ≈60 s proxy window, tens of ms time-to-denial) are properties of our
  instruments: polling intervals, and a proxy configuration we wrote. They are
  not properties of CSS or of Solid.
- **Recipients are our code.** The aggregator, the retrieval memory, the
  cooperating and non-cooperating handlers, and the notice format were written
  for this experiment. The P2 config B proxy is deliberately permissive and is
  not claimed to be common.
- **One engine configuration in P4:** Comunica link traversal 0.8.0 with
  default settings and one query shape. A lenient mode that tolerates failed
  links was not run.
- **A small model in P6/P7:** `qwen2.5:3b`, chosen by the User instead of the
  planned `qwen2.5:7b-instruct` (see `ENVIRONMENT.md`), with 10 invented facts.
  Retrieval, the primary measurement, does not depend on the generator.
- **Notice v2 models the consent status imperfectly, on purpose.** DPV
  reserves `dpv:ConsentWithdrawn` for withdrawal by the data subject. In the
  notice, the declared data subject is the fictional person in `person.ttl`,
  and the sender is alice (`SPEC_VS_IMPL.md` P7-6; kept at the User's
  decision).
- **Long expiry not observed.** The default channel lifetime of 20160 min is
  the advertised `endAt`. 14 days cannot be observed within a run.
- **Synthetic data.** All personal data is invented. The fixture's
  appointment is a passport renewal, which keeps the fixture clear of health
  data.
